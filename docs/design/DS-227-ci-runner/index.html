desk-q: the CI runner

desk-q says nothing about the CI runner, the Tart VM that runs Voice PA's checks on this Mac. You can't see whether it's up, whether it's running jobs, or that it's the reason no worker can start. Below are the screens as they would look, built on the approved DS-227 screens rather than today's desk-q. Nothing is built until you approve it.

◆ waiting for your sign-off

What desk-q shows today

2/10desk-q reads the CI runner's effects but never names it, so when it stalls a batch you're left guessing at the cause.

Critical

  1. "Room for N more" leaves out the CI runner's memory. desk-q works it out from raw free memory (desk-q.mjs:719). The spawn ladder first subtracts the runner's reservation (ladderMemory, desk-env.mjs:901). On 25 Oct the ladder was at 0 GiB against an 8 GiB gate, with about 20 GiB free, while desk-q still showed room.

Important

  1. Up or down is never shown. You only find out with desk-runner status or tart list.
  2. Running jobs aren't shown either. Four slots for Voice PA can be busy or idle, and nothing on screen tells the two apart.
  3. A landing PR whose check waits for the VM reads Linux: no runner, 12m. It doesn't say the CI runner is down, or whether anything will bring it back.

What works

  1. The landing state (DS-194) already finds a check queued with no runner after 10 minutes. This proposal names the reason.
  2. desk-runner status already knows everything below. It just isn't written anywhere desk-q can read it.

Four rules

  • One name: "CI runner". It's never just "runner". DS-227 already uses "who runs the batch" for the supervisor or a session, and a bare "runner" would read as that.
  • Up or down is in the words, not only the colour. The line always says up, down, asleep or waking, so it reads the same in --plain.
  • The colour comes from the consequence. Down with nothing queued is dim, because you keep it down on purpose until DS-253. It turns ◆ magenta only when a check is queued for it and nothing will start it, which is DS-227's "nothing moves until you act". It turns ✕ red when it can't run safely (the isolation check failed) or keeps failing to restart.
  • "Working" means slots running jobs, named by PR. The header line counts them, and r opens a screen that lists each slot's job.

Colours are DS-227's key: green moving, cyan in flight, blue ready, amber warning, magenta needs you, dim held or a label, red failed. The amber edge on a line marks what this proposal adds to the DS-227 screen.

The deeper view is GitHub's own. The CI runner has no web page of its own, and it doesn't need one. A job on the local VM shows on github.com exactly like a hosted job, with the same live log step by step. So enter on a slot opens that job's page in your browser, mid-run. w opens the repo's Settings → Actions → Runners page, where GitHub marks each slot Idle, Active or Offline. In plain output, the URL is printed instead.

Example rows. This is where "is it actually doing anything" gets answered in full. When the VM is down, the slot table is replaced by one line saying what's queued for it and the command that starts it. The screen only reads. Like DS-227's U12, desk-q runs no command that changes the VM, so starting and stopping stay with desk-runner, and the screen names the commands.

One choice: where the CI runner goes on home

Option A · recommended · shown above

Its own header line, under the workers line

It sits beside the other machine-wide line. The memory link reads straight down: "room for 0", then "idle, holding 24 GiB". The repo table stays about repos.

Costs one line of height when a CI runner exists, and none when it doesn't.

Option B

A "CI runner" row in the repo table

You could select it with the arrow keys and open it with enter, the same as a repo.

But LAST PASS, RUN, READY, WAIT and the other columns mean nothing for it, so it would be a row of dashes. It also puts a machine resource in a list of repos, and the memory cause ends up four lines away from "room for 0".

How desk-q knows, with no model and no tokens

Up or down
One tart get per refresh, which desk-env's runnerState() already does for the pass.
Memory held
ladderMemory(), the pass's own figure, so desk-q and the spawn gate can't disagree.
Slots and jobs
New: desk-runner keep, which launchd already runs every minute, writes runner/status.json. It holds each slot's state, job name (from the slot's own log, at no API cost), PR and the job's page on GitHub (one API call per job started, within DS-61's budget), recent finished jobs, the gate reason and the restart backoff.
Will anything start it
Whether the keep agent is loaded: one launchctl print, as DS-227 already does for the supervisor.
Which checks need it
New: the status file records each repo's DESK_RUNS_ON routing, read once an hour. A queued Linux check in a repo routed to local is waiting for the CI runner. The pass records today only whether a check has a runner (pass.mjs:1384).
Isolation and restarts
isolation.status and restart.backoff, which desk-runner status already reads.

Not changing

  • DS-227's screens, colours, red band and notes rules. This only adds to them.
  • What the CI runner does. Sleep and wake (DS-249), memory turns (DS-252) and the claim (DS-253) are their own tickets. This shows their states once they ship.
  • desk-q stays read-only for the VM. It names desk-runner up, down and scale and doesn't run them.
